# 13 A* (콘솔)

## 목표

격자 위의 **A\* 길찾기**를 콘솔에서 완성합니다. 00단계 소코반처럼 렌더링 없이 규칙(알고리즘)만 먼저 만들고 테스트로 검증합니다. 14단계에서 이 코드를 그대로 소코반 맵에 연결합니다.

알고리즘 설명은 수업 슬라이드를 참고하세요.

## 배울 개념

- **g, h, f:** g = 시작에서 지금까지 실제 거리, h = 목표까지 추정 거리(휴리스틱), f = g + h. f가 가장 작은 칸부터 넓혀 갑니다.
- **open / closed:** open은 "후보", closed는 "최단 거리가 확정된 칸"입니다.
- **맨해튼 거리:** 4방향 이동에서 `|dx| + |dy|`는 실제 거리보다 절대 크지 않습니다(admissible). 그래서 A\*가 최단 경로를 보장합니다.
- **경로 복원:** 칸마다 "어디서 왔는지(cameFrom)"를 기억했다가 목표에서 거꾸로 따라갑니다.
- **BFS와 비교:** 같은 최단 경로를 찾지만, A\*는 목표 쪽으로 치우쳐 탐색해서 훨씬 적은 칸을 봅니다.

## 테스트가 검사하는 것

경로의 **모양**은 검사하지 않습니다. 길이가 같은 최단 경로가 여러 개일 수 있기 때문입니다. 대신 다음을 봅니다.

1. 찾았는지 여부가 맞는가
2. 경로가 올바른가 (start에서 시작해 goal에서 끝나고, 한 칸씩 상하좌우로, 막힌 칸을 지나지 않음)
3. 길이가 BFS로 구한 최단 거리와 같은가

## 예측 질문 (SPEC.md에 실행 전 답을 적는다)

1. `Heuristic`이 항상 0을 돌려주면 A\*는 어떤 알고리즘이 될까? 탐색한 칸 수는 어떻게 달라질까?
2. `Heuristic`을 맨해튼 거리의 3배로 하면 경로가 여전히 최단일까? 탐색한 칸 수는?
3. `closed`인 칸을 꺼냈을 때 건너뛰지 않으면 어떤 일이 생길까? (같은 칸이 open에 여러 번 들어갈 수 있는 이유)
4. `maps/wall.txt`에서 A\*가 벽 앞에서 헤매는 이유는? `maps/open.txt`와 탐색한 칸 수를 비교해 보자.
5. 동점일 때 h가 작은 것을 먼저 꺼내지 않고 f만 비교하면 `maps/open.txt`의 탐색한 칸 수는 어떻게 될까?
