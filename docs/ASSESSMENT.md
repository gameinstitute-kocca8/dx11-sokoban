# 평가

평가는 "코드가 있는가"가 아니라 **"내 코드를 소유하고 있는가"**를 봅니다. 소유란 코드의 목적과 경계를 설명할 수 있고, 고장 났을 때 원인을 찾아 고칠 수 있다는 뜻입니다.

## 단계별 (매 단계)

| 항목 | 증거 |
|---|---|
| 통과 조건 | `CHECKLIST.md` 항목, CI 결과(빌드, 테스트, `my-screens`) |
| 작업 순서 | git 히스토리: SPEC 커밋이 구현보다 먼저 있는가 |
| 예측 | `TASK.md` 예측 질문에 대한 사전 답과 실행 결과 비교 |
| 기록 | `LOG.md` 1~2건 |
| 데모 질문 | `CHECKLIST.md`의 "설명할 수 있어야 하는 것" |

## 최종 시연 (1인 10~15분)

### 1. 고장 내기 (10분)

강사가 학생의 코드에서 한 곳을 몰래 망가뜨립니다. 학생은 실행 결과와 로그, 디버그 도구로 원인을 찾아 고칩니다.

- 정답을 맞히는 것보다 **어떻게 좁혀 갔는지**를 봅니다.
- AI는 써도 됩니다. 다만 질문을 어떻게 좁혔는지 함께 봅니다.

### 2. 구조도 (2분)

보지 않고 다음 두 가지를 그립니다.

- 레이어 의존 방향: Game → Engine → Render, 각 레이어의 대표 클래스
- 한 프레임의 흐름: 입력 → 규칙 → 상태 → Draw

### 3. 작은 변경 (3분)

강사가 다음 중 하나를 요청하면, 자기 코드에서 바로 수정합니다.

- 레벨에 상자 하나 추가 또는 벽 위치 변경
- 목표 판정 규칙 수정
- 카메라 offset 변경
- Constant Buffer 값(색, 크기) 변경

## AI 활용 루브릭

채용에서 보는 AI 활용 능력은 "AI로 코드를 빨리 얻는 것"이 아니라 **AI의 답을 좁히고, 의심하고, 증거로 확인하는 것**입니다. 도구 종류나 유료 여부는 점수에 영향이 없습니다.

| 항목 | 1 (부족) | 2 (보통) | 3 (좋음) | 증거 |
|---|---|---|---|---|
| 질문 | "안 돼요, 고쳐 줘" 수준. 파일 통째로 붙임 | 기대와 실제, 관련 함수 하나를 담음 | 내 가설과, 답을 받으면 할 검증까지 담음 | `LOG.md`의 질문 원문 |
| 판단 | AI 제안을 그대로 붙임 | 일부를 이해하고 고쳐 씀 | 근거를 들어 거절하거나 더 나은 대안을 냄 | `LOG.md`의 채택/수정/거절, 데모 질문 |
| 검증 | 실행해 보기만 함 | 테스트나 화면으로 확인 | 실패하는 조건(반례)까지 만들어 확인 | 테스트 출력, 내 시나리오, `REVIEW.md` |
| 설명 | 바꾼 이유를 말하지 못함 | 내 말로 이유를 설명 | 다른 방법과 비교해 왜 이게 맞는지 설명 | 데모 |

- 13단계의 **AI 검증 과제**(`REVIEW.md`)는 이 루브릭의 "판단"과 "검증"을 직접 보는 과제입니다.
- 최종 시연의 고장 내기에서는 학생이 자기 AI 도구를 써도 되고, 교수자는 그 화면을 함께 보며 질문을 어떻게 좁히는지 관찰합니다.

## 하지 않는 것

- AI 사용 여부를 추궁하거나 출처를 단정하지 않습니다.
- 정답 코드와의 유사도로 평가하지 않습니다.
